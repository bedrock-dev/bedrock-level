# Bedrock `AabbVolumes` 数据格式（LevelDB key `0x77`）

> 本文档根据一个包含 `minecraft:trial_chambers` 的实际样本整理：
> `0x260000000b00000077.bin`，大小为 570 字节。
>
> 目前只有一个样本，因此已确认字段和推测字段分开描述。标记为“待确认”的字段，
> 不应在写回数据时擅自修改。

## 1. 数据定位

这不是独立的 NBT 文件，而是 LevelDB 某条记录的 value。文件名是把原始 LevelDB
key 转换成十六进制后的结果，`.bin` 是导出工具附加的扩展名。

文件名去掉 `0x` 后按字节拆分：

```text
26 00 00 00 | 0B 00 00 00 | 77
```

Bedrock 区块 key 使用小端序：

| 字节范围 | 含义 | 值 |
| --- | --- | ---: |
| `0x00..0x03` | 区块 X 坐标 | `38` |
| `0x04..0x07` | 区块 Z 坐标 | `11` |
| `0x08` | key 类型 | `0x77`（119） |

`0x77` 是 AabbVolumes 数据。它与普通区块地形 key 不同，但仍以区块坐标
作为 key 的前缀。其他维度的 key 通常还会在 key 类型前包含 4 字节维度值。

## 2. 总体布局

所有整数均为 little-endian `int32`，字符串使用 UTF-8：

```text
int32       format_version       = 1
int32       unknown_0             = 1
int32       unknown_1             = 0
uint16      name_length           = 24
byte[24]    feature_name          = "minecraft:trial_chambers"

int32       box_count             = 13
Box[13]

int32       triple_count          = 13
int32[3][13] triples
int32       trailing_value        = 0
```

样本中的偏移：

| 偏移 | 大小 | 类型 | 样本值 | 状态 |
| ---: | ---: | --- | --- | --- |
| `0x000` | 4 | `int32` | `1` | 版本候选字段 |
| `0x004` | 4 | `int32` | `1` | 含义待确认 |
| `0x008` | 4 | `int32` | `0` | 含义待确认/保留字段 |
| `0x00c` | 2 | `uint16` | `24` | 名称长度 |
| `0x00e` | 24 | UTF-8 | `minecraft:trial_chambers` | 结构名称 |
| `0x026` | 4 | `int32` | `13` | 包围盒数量 |
| `0x02a` | 364 | `Box[13]` | 13 个 28 字节记录 | 结构片段信息 |
| `0x196` | 4 | `int32` | `13` | 三元组数量 |
| `0x19a` | 156 | `int32[3][13]` | 13 个三元组 | 含义待确认 |
| `0x236` | 4 | `int32` | `0` | 尾字段，含义待确认 |

文件总大小为 `0x23a`（570）字节。

## 3. 包围盒记录

每条记录占 28 字节：

```text
int32       entry_value
int32       min_x
int32       min_y
int32       min_z
int32       max_x
int32       max_y
int32       max_z
```

`entry_value` 在该样本中依次为 `13, 12, ..., 1`。它很可能与结构片段的引用数、
层级或序号有关，但仅凭此样本还不能确定。

| 序号 | entry_value | 最小坐标 (x,y,z) | 最大坐标 (x,y,z) |
| ---: | ---: | --- | --- |
| 0 | 13 | (620, -12, 184) | (622, -11, 186) |
| 1 | 12 | (620, -10, 184) | (622, -10, 186) |
| 2 | 11 | (619, -17, 183) | (623, -6, 191) |
| 3 | 10 | (620, -30, 185) | (623, -23, 189) |
| 4 | 9 | (620, -30, 176) | (623, -23, 179) |
| 5 | 8 | (613, -38, 186) | (614, -37, 188) |
| 6 | 7 | (613, -38, 181) | (614, -37, 183) |
| 7 | 6 | (612, -34, 176) | (612, -30, 179) |
| 8 | 5 | (613, -28, 176) | (614, -27, 178) |
| 9 | 4 | (615, -39, 176) | (619, -23, 180) |
| 10 | 3 | (618, -18, 182) | (623, -5, 191) |
| 11 | 2 | (613, -40, 176) | (623, -22, 191) |
| 12 | 1 | (608, -45, 176) | (623, -5, 191) |

这些坐标与 key 中的区块 `(38, 11)` 一致：

```text
chunk X range = [38 * 16, 38 * 16 + 15] = [608, 623]
chunk Z range = [11 * 16, 11 * 16 + 15] = [176, 191]
```

最后一条包围盒覆盖整个区块的 X/Z 范围，Y 范围为 `-45..-5`，与试炼密室位于负
Y 高度的特征相符。包围盒应按闭区间理解，尺寸计算为 `max - min + 1`。

## 4. 三元组区域

偏移 `0x196` 处为数量 `13`，随后是：

```text
(13, 0, 0)
(12, 0, 0)
(11, 0, 0)
(10, 0, 0)
( 9, 0, 0)
( 8, 0, 0)
( 7, 0, 0)
( 6, 0, 0)
( 5, 0, 0)
( 4, 0, 0)
( 3, 0, 0)
( 2, 0, 0)
( 1, 0, 1)
```

它们的形状像结构片段引用、连接信息或生成状态记录，但目前不能确认三个整数
分别代表什么。不应直接将它们当作世界坐标。

## 5. 与 NBT 的区别

该 value 不是 NBT：

1. 第一个字节是 `0x01`，不是 Compound Tag 常见的 `0x0a`。
2. 数据没有 NBT 的 tag type/name/value 递归结构。
3. 坐标区域呈现固定的 32 位小端整数排列。
4. 字符串前的长度字段是普通二进制结构中的长度字段，不代表 NBT String Tag。

因此不能直接交给 NBT parser。解析器应先根据 LevelDB key 的最后一个字节判断为
`0x77`，再使用本格式读取 value。

## 6. 解析伪代码

```cpp
read_i32(format_version);
read_i32(unknown_0);
read_i32(unknown_1);

auto name_length = read_u16();
auto feature_name = read_bytes(name_length);

auto box_count = read_i32();
for (int i = 0; i < box_count; ++i) {
    auto entry_value = read_i32();
    auto min_x = read_i32();
    auto min_y = read_i32();
    auto min_z = read_i32();
    auto max_x = read_i32();
    auto max_y = read_i32();
    auto max_z = read_i32();
}

auto triple_count = read_i32();
for (int i = 0; i < triple_count; ++i) {
    auto a = read_i32();
    auto b = read_i32();
    auto c = read_i32();
}

auto trailing_value = read_i32();
```

实际实现时应检查 count 非负、长度不越界、不会整数溢出，并确保读取结束后的 offset
正好等于 value 长度。未确认字段应原样保留，以免破坏游戏后续读取。

## 7. 如何进一步确认字段

仅凭这个样本可以可靠确认名称、包围盒和整体长度，但无法可靠命名所有字段。建议
收集以下样本进行差分：

- 同一个试炼密室相邻区块中的多个 `0x77` value；
- 没有结构的区块，确认 key 是否不存在或 value 是否为空；
- 村庄、远古城市等其他结构的 `0x77` value；
- 结构刚生成、部分区块被加载、结构完全生成后的同一区域数据。

重点观察 `entry_value`、三元组和包围盒数量随结构生成状态的变化。
